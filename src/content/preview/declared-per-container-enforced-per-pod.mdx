A pod with two containers kept getting evicted. Container foo requested about 14 GiB of ephemeral storage and declared no limit. Container bar declared a 6 GiB limit, and every new pod died once their combined usage passed 6 GiB. The 6 GiB was written under bar, but kubelet applied it to the whole pod.

A storage limit has two scopes that are easy to conflate: the scope it is declared on, and the scope kubelet enforces it against. For ephemeral storage they are not the same, and nothing in the YAML tells you which one you are setting.

## Why a per-container limit became the pod's budget

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: potato
spec:
  containers:
    - name: foo
      resources:
        requests:
          ephemeral-storage: 14Gi
        # no limits.ephemeral-storage, so this container adds
        # nothing to the budget but its usage still counts
      volumeMounts:
        - name: foo-data
          mountPath: /var/data

    - name: bar
      resources:
        limits:
          # the pod's only ephemeral-storage limit, so this
          # 6 GiB becomes the budget for both containers
          ephemeral-storage: 6Gi
      volumeMounts:
        - name: bar-data
          mountPath: /var/data

  volumes:
    # no medium field, so both volumes are disk-backed
    - name: foo-data
      emptyDir:
        sizeLimit: 14Gi   # foo's ceiling, checked alone
    - name: bar-data
      emptyDir:
        sizeLimit: 6Gi    # bar's ceiling, checked alone
```

Kubelet runs its local storage checks in `localStorageEviction`, gated by a single `localStorageCapacityIsolation` flag. The pod-level check compares two quantities.[^checks]

<Formula>
  <FormulaLine term="usage">foo + bar + kubelet-accounted local ephemeral storage</FormulaLine>
  <FormulaLine term="budget">effective PodLimits aggregate = 6 GiB</FormulaLine>
</Formula>

Usage is the pod's total, measured whether or not a container declared anything. The budget comes from `PodLimits`, which for regular containers is `AggregateContainerLimits`, folding each container's limit map into a running total with `addResourceList`.[^aggregate] That loop visits only the keys present in each map. A container without one contributes usage and no budget.

When this fires, the event names the cause directly: "Pod ephemeral local storage usage exceeds the total limit of containers".[^event]

## When only some containers declare a limit

If no container declares one, the key never appears and the check returns early without comparing anything.[^early] If every container declares one, the budget covers everything that can produce usage.

The partial case is the trap. The budget reflects part of the pod while the usage reflects all of it. Adding a limit to a single container is enough to put a pod there.

## emptyDir.sizeLimit is enforced per volume

A disk-backed emptyDir never joins that aggregate. `emptyDirLimitEviction` compares each volume against its own size limit, and only when that limit is present and positive.[^emptydir] Nothing is summed, so one volume's usage is never measured against another volume's limit.

Use it when the boundary you want is one dedicated volume per container. The threshold is per volume, but the consequence is not: crossing it evicts the whole pod.

## Neither field is a quota

What happens when you cross one shows why.

| Field | Crossing it causes | Checked by |
|---|---|---|
| `limits.ephemeral-storage` | pod eviction | kubelet, on its sync interval |
| `emptyDir.sizeLimit` | pod eviction on disk, a failed write on tmpfs | kubelet on disk, the kernel on tmpfs |

<FigCaption>Source links throughout point to Kubernetes [v1.35.0](https://github.com/kubernetes/kubernetes/releases/tag/v1.35.0).</FigCaption>

Only the tmpfs case refuses the write.[^tmpfs] Everywhere else the bytes land and the pod dies afterward, on kubelet's next pass. A request is not an option either, since it only affects [placement](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#how-pods-with-resource-requests-are-scheduled).

Coverage is partial too. An emptyDir threshold sees only what is written under that mount. The container's writable layer sits outside it, and so do its standard output and error logs. A volume with no size limit can still fill the node through a separate eviction path.

Pod-level resources do not close the gap, since they cover CPU, memory, and hugepages but not ephemeral storage.[^podlevel]

Before adding an ephemeral-storage limit to any container, read what the other containers in that pod declare. If they declare nothing, **the limit you are adding is not that container's ceiling. It is the pod's.**

[^tmpfs]: A memory-backed emptyDir is mounted as tmpfs. Kubelet passes a [size= mount option](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/volume/emptydir/empty_dir.go#L573-L577) built from the [smaller of the volume's size limit and the pod's memory allocation](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/volume/emptydir/empty_dir.go#L114-L140). The kernel enforces that ceiling directly.

[^podlevel]: The [pod-level resource specification](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#pod-level-resource-specification) lists only CPU, memory, and hugepages. The v1.35.0 resource helper enforces the same set in [supportedPodLevelResources](https://github.com/kubernetes/kubernetes/blob/v1.35.0/staging/src/k8s.io/component-helpers/resource/helpers.go#L65-L69).
