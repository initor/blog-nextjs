重新推敲的根因

此前的说法是「整条链路没有任何一处做等价性检查」。这不准确。检查是存在的。

codegen 对整数字段的边界确实有守卫：如果边界不是整数，直接拒绝。而 263 作为 float64 是一个完完整整的整数，所以它通过审查，一路放行。

同一个值，同一个位置，两个不同的问题。护栏问的那个问题本身是合理的，只是它守的不是这道门。

所以论点不是「没人检查」，而是 「有人检查了，检查了错的那个不变量」。配上 Go 编译器那一拍，全文就有了两道护栏：一道问错了问题，一道问对了问题但够不着那个值。

同时要澄清一件事：float64 是结构性的，不是 codegen 的失误。marker 类型本身就声明为 float64，而目的地是上游 Kubernetes API 类型里的 Maximum *float64。codegen 无处可放这个数。post 里不能把它写成 codegen 的 bug。

发布前请对着你实际锁定的版本复核那段守卫代码的确切写法。上述结论来自一次上游源码检索，结论可靠，但行号与函数名会随版本漂移。

三层规范的沉默

这个缺陷之所以能一路走到生产，是因为每一层都假设另一层管了这件事。

JSON 说了

RFC 8259 第 6 节：整数落在 [-(2^53)+1, (2^53)-1] 区间内才「可互操作，各实现会在数值上完全一致」，并建议不要期待超过 IEEE 754 binary64 的精度与范围。

最强的引用来源。规范层面把话说得很清楚。

JSON Schema 主动免责

2020-12 第 6.2.2 节：maximum 的值必须是一个 number，而不是 integer。第 4.2 节明确表示 JSON Schema 不对精度施加任何边界。

不是遗漏，是声明这不归它管。

OpenAPI 只字未提

3.0.3 把 int64 定义为「signed 64 bits (a.k.a long)」，对精度限制与 IEEE 754 完全没有提及。

这是真正的空白：它承诺了 64 位语义，却把边界字段建立在一个只有 53 位的载体上，而没有对这个矛盾说一个字。

Kubernetes API Conventions 说了，但在别处

「Primitive types」一节写明：所有数字会被 JavaScript 转成 float64，int64 字段必须做边界检查限制在 -(2^53) < x < (2^53)，超出的应当以字符串序列化。

但它管的是 Go 字段设计与序列化，字面上从未提及 OpenAPI 的 maximum 关键字或 marker。引用时必须说明这是外推，不能暗示文档已经覆盖了这个场景。

CRD 文档 / marker 参考 完全没有

CRD 文档的校验章节、api-concepts 页面、以及 marker 参考手册里，一个字都没提精度。

手册甚至没有写明 Minimum / Maximum 接收的是 float64：那一栏是空的，而旁边的 MinItems 写着 int。使用者根本无从得知自己正在往一个浮点数里塞整数。

链条是完整的：JSON 说清楚了 → JSON Schema 声明不管 → OpenAPI 沉默 → Kubernetes 在一份讲 Go 字段的文档里说了 → 面向使用者的 marker 文档一字未提。规范说过的话，没能走到写 marker 的人面前。

诚实边界：同样的 263 边界也出现在若干 CRD 派生的 JSON schema 里，但其中一个项目的源 CRD 根本没写 maximum。那些边界是下游的 CRD 转 JSON Schema 工具注入的。同类缺陷，不同生产者，不能当成 codegen 的产物呈现。

重点在于 venue 比 CRD 更宽：这是一个 OpenAPI 全域的缺陷类，任何把整数边界塞进 float64 的工具链都会中招。这也正好是把读者从「Kubernetes operator 作者」扩展到「所有写 API 的人」的那把钥匙。

为什么它没有被大规模发现

架构分歧要求取整后的值跳出 int64 范围。实测下来，那个窗口窄得出奇。

marker 写的值取整后精确跳出 int64
253 − 19007199254740991是否
5 × 10185000000000000000000是否
2624611686018427387904是否
MaxInt64 − 5129223372036854774784否否
MaxInt649223372036854775808否是

所以有两种失效模式，只有第二种跟架构有关。253 到 263 之间，边界被悄悄近似但仍在 int64 内，实际上限略有偏差而无人在意。只有在 int64 范围最顶端的几百个值里，取整后的边界才会跳出去。

而 MaxInt64 恰恰是一个认真的人，在 lint 规则要求「必须写 Maximum」、而这个字段又没有真实上限时，会伸手去拿的那个值。

你为了表达「没有上限」而选中的那一个数，是整个范围里唯一会引爆的数。

还有一层不对称值得写进去：同一个「无实际上限」的习惯用法，在 32 位上是 2147483647，完全安全，因为 MaxInt32 远低于 253，穿过 float64 毫发无损。这个习惯平移到 64 位就静默失效了。不是有人写错了，而是一个正确的习惯换了个位宽。

这篇 post 因此可以是什么

把以上叠起来，定位应该往上调一档。

这不是「我踩了个坑」。这是一个 OpenAPI 全域的缺陷类，活在公开 spec 里，规范没写，上游没人报过，而现有的那道护栏检查了错的属性。

四个可执行的推论：

一，扩大读者。冷开场之后一句话把非 Kubernetes 读者留下来，用已被证实的 Twitter id_str 先例。Discord 不能照「同样原因」引用，他们给出的理由是防止整数溢出，从未提及 53 位。

二，重构论点。围绕两道护栏来写：一道问错了问题，一道问对了问题但够不着。这比「没人检查」强一档。

三，提一个上游 issue。发布前做，文末链接它。这是全文最便宜也最重的一笔。

四，脚注引 RFC 8259 第 6 节，并点名 OpenAPI 的沉默是规范空白。
