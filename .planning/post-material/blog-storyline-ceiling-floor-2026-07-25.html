故事线：五次纠正

这篇 post 不是按时间顺序讲一个 bug，而是按读者认知的顺序拆掉五个错误直觉。每拆一个，读者就被往「类型」推近一步。

论点

这个 bug 的每一步都由一个行为正确的组件完成，跨越了三个进程、两种 CPU 架构和一次 git 提交。发现它的地方和造成它的地方，中间隔着一个持久化边界。真正难的不是路径长，而是沿途没有任何一处是坏的。缺陷住在两个类型系统交接的缝里，而那道缝上没有任何人设检查。

推论：这个 bug 无法用二分定位，因为不存在一个「坏的提交」。也无法用 debugger 抓，因为有一半的执行躺在 git 里。

五次纠正

这五个误读不是假想的。它们是在向一个已经理解这套系统的人口头解释时，按这个顺序真实出现的。每一个都是聪明人会走的弯路。

BEAT 01

「CI 抖了」

读者此刻相信
同一个 commit 一会儿过一会儿不过，那就是基础设施问题。
真相
一个平台是真的在因为真实原因失败。恰好另一个 job 是无关的取消，让错误判断显得更可信。
叙事作用：房子的招牌动作，先立一个假嫌疑人，两个字杀掉。这也是作者当时真实走过的弯路，写进去读者才会信任后面的推理。
BEAT 02

「YAML 是文本，所以丢精度」

读者此刻相信
序列化成文本的过程是有损的。
真相
文本是整条链路里唯一不丢精度的部分。19 个字符把这个值存得好好的。
叙事作用：第一次把读者的注意力从「文件格式」上撬开。
BEAT 03

「两个解析器读同一个字符串，结果不同」

读者此刻相信
codegen 和 apiserver 对同一份输入产生了分歧。
真相
它们从来没读过同一个字符串。codegen 读 …807，apiserver 读 …000。两次解析都是确定性的，而且都是对的。
叙事作用：最有价值的一拍。纠正它，读者才会去看数据模型而不是文件格式。两串都是 19 位数字，长度一样，所以 diff 里看不出来，这个细节值得点出来。
BEAT 04

「精度是序列化的时候丢的」

读者此刻相信
写出去的那一刻被四舍五入了。
真相
值在进入 float64 的那一刻就已经没了。序列化器把手上的 float64 打印得完全正确，9223372036854776000 正是能唯一还原回 263 的最短十进制写法。
叙事作用：与 BEAT 03 并列的核心。推论很实用：去修序列化器什么也修不好，到那一步原始数字已不可恢复。
BEAT 05

「这是 x86 的问题」

读者此刻相信
架构差异导致了这个 bug。
真相
架构只决定可见性。值在每一台机器上都已经是错的。ARM 之所以正常，是它的饱和行为恰好把损坏又还原了回去，一个未定义行为抵消了另一个。
叙事作用：收口。把「级联后果」和「根因」彻底分开，读者才不会带着错误结论离开。

五个误读指向同一个方向

三个误读的方向完全一致，都把人推向文件格式。这不是巧合，而是「YAML 里有个数字看起来不对」这个现场本身在误导。整篇 post 的结构任务，就是反复把读者从文本拉回类型。

章节骨架

五节，句子式小标题，单独列出来能读成一条故事线。对照房子里最新一篇的写法。

  1. A bound that looked harmless

    marker 本身，以及那条催生它的、本身合理的 lint 规则。冷开场落在这一节之前，不带标题。

  2. The first suspect

    假嫌疑人：基础设施抖动。两个字杀掉，然后点名那个从没写下来的假设：源码里写的数字，就是 apiserver 执行的数字。

  3. The number on disk

    第一阶段，四舍五入，与架构无关。BEAT 02 到 04 都在这里拆。提交进 git 的那行 YAML 是本节的实证。

  4. Where the architectures disagree

    第二阶段，窄化转换。Go 规范原文进 <Callout>，六字节汇编收尾。BEAT 05 在这里。

  5. The fix

    去掉上限，253 规则，repro 链接，最后一句格言。不写 Conclusion。

标题建议 I Capped the Wrong Integer（第一人称认错句式，对齐最新一篇），slug 保留数字钩子 ceiling-that-became-a-floor。

证据落点

每条都在本次调查中实证过，按上面的节次分配。

证据落在

Go 程序输出：float64 往返后变成 263第 3 节

房子的规矩

硬约束说明
零 em dash任何形式都不行，用逗号同位语或分号替代
只用 ##正文无 #，无 ###
正文零 bullet list枚举写成句子
无 Conclusion / Summary 小节结论就是最后一句
冷开场无标题，2 到 3 句，100 字内亮论点
一个 <Callout>放权威原文，随后跟一句平直的解读
一张图 + <FigCaption>图注写结论，不描述画面
repro 链接指向 GitHub tree 目录，不是站点上的 main.go
脚注常量一律注到上游源文件，放正文最末

素材文件本身用了 bullet 和表格，那是为了速查。post 一个都不能用。不要把笔记的形态当成结构模板。

不写什么

技术内容全部可公开，它是 JSON Schema、OpenAPI、Go 和 CPU 指令语义的性质，不涉及任何专有信息。但来源工作是内部的。

不要出现：内部 CRD 类型名或字段名、这个字段所属的功能或控制器、内部 PR 编号、内部 ticket ID、内部 CI job 或镜像名、内部仓库路径、内部编码规范文档。需要背景时就说「我维护的一个 Kubernetes 控制器」，字段用中性的 someGeneration。

唯一值得泛化而不是删掉的，是那条「数值字段要同时写 Minimum 和 Maximum」的规范。把它描述成一条常见且合理的 lint 规则，不要指向具体文档。它是全文最后一层张力：一条好规则可以是直接诱因。
